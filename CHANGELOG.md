# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

The first release: the Rust library both Gerfaut apps are built on. It does everything a watch-only wallet needs and nothing with keys: there is no code to generate a key, handle a seed or sign a transaction.

### Added

- Output descriptors as the single internal format. Extended keys, SLIP-132 keys (`zpub`, `vpub`, `Zpub` and the rest), single public keys, plain addresses and multisig setups all become a descriptor. A pair of receive and change descriptors must describe the same wallet.
- Import from text, pasted or read from a file, or from a static or animated QR code (UR and BBQr). Besides descriptors, keys and addresses, the parser reads a BSMS record (BIP-129), a payment URI, a Sparrow descriptor file and a JSON wallet export such as Coldcard's. It recognises the format on its own and reports whatever it had to assume or rewrite, so the app can ask before it stores anything. An animated code is read one frame at a time, in a scan the core holds for the app: the last frame of a long code costs no more than the first.
- Address derivation with a configurable gap limit. Upcoming receive addresses skip any address a payment already reached, and every sync reads past the last revealed address up to the gap limit, so a payment to an address handed out elsewhere shows without a rescan. A full rescan stays available, and so does watching a single address.
- Balances, transaction history and UTXOs over Esplora or Electrum: a public server, picked by name or in automatic rotation, or a server of your own. A sync fetches only what the wallet lacks, and reads every script again when the vault opens and once a day.
- In the automatic rotation, a server that is down while a later one answers is tried last for 5 minutes, then twice as long each time it fails again, up to an hour. Only an outage counts, and the server of the live watch is never put behind another.
- An Electrum sync asks for full lists 50 requests at a time, and transactions 40 at a time. When Blockstream's electrs refuses a batch as too large or out of budget, the sync asks for one transaction at a time, or waits as for a rate limit.
- Electrum over TLS with trust on first use: a self-signed certificate is pinned by its fingerprint and refused if it ever changes.
- Miniscript policy analysis. A descriptor reads as named spending branches with their keys, thresholds and timelocks, and each lock is measured against the chain height and the device clock. The branches come in the order a person reads them: the primary paths first, then the recovery, the emergency and the other ones, each from the nearest to the farthest. Each one carries its tone, so both apps show it in the same colour: open now, opening in under 30 days, or neutral. The unspendable internal key of a Liana vault is read as such.
- Transaction and PSBT preview, then broadcast through the configured backend. The preview warns on missing signatures, on amounts no backend could confirm, and on `SIGHASH_NONE` or `SIGHASH_SINGLE` signatures (`uncommitted_outputs`). A PSBT still missing signatures gets its fee rate estimated once signed (`FeeRateBasis`), and a transaction already in the mempool reads `in_mempool`, safe to send again. A coin shown spent in a block stops the broadcast only once the core has checked that the spending transaction does spend it.
- The preview and the broadcast follow the order of the syncs: with the automatic backend and the live watch on, the watch's operator first. Only a transport failure moves on to the next server, and a node's refusal ends there. The txid a server returns must match the one the core computes, and "already known" counts as sent once the same server returns the transaction. The vault keeps the last 10 transactions broadcast, so an app can check where each one stands after a restart.
- A built-in Tor client (arti) behind the `embedded-tor` feature, exposed as a local SOCKS5 proxy, so a `.onion` backend works on a machine with no Tor daemon. Without the feature, `.onion` hosts go through a system Tor.
- A live watch on the wallet manager. It keeps one connection to the backend: Electrum subscriptions, a mempool WebSocket, or polling of any other Esplora. It follows up to 200 scripts per wallet and 2,000 in all, or 20,000 on a backend marked `own_node`, shares them out rank by rank with pinned wallets first, and reports each wallet's coverage in `WatchStatus`. For the addresses it leaves to the syncs, the status gives the reason (the watch's own limit, or a server that refused them), the limits in force and, when the server refused them, the setting of the server software to raise. With the automatic backend, syncs go first to the watch's server, so a single operator sees the wallet's addresses, and the opening sync waits for the watch's first session, 20 seconds at most.
- The watch keeps 32 subscriptions in flight, 256 on a backend marked `own_node` unless it runs ElectrumX. A server that refuses the watch for cost from the handshake on is left alone for a quarter of an hour, except the user's own node. When a session goes 2 hours without a new block, the tip of another Electrum server of the same operator is read, and the watch moves there if its own server lags 2 blocks or more.
- A confirmation the watch hears of over Electrum is proven in its block on the same connection and taken without a sync. A history that does not hash to the status the server announced, and leaves out a transaction the wallet holds, is set aside until the next sync.
- Live alerts: each transaction is handed out once when it enters the mempool and once when it confirms, and the vault remembers what was announced across restarts. A fee bump is not announced again (`replaces` names the first txid), and an incoming payment that leaves the mempool is announced as dropped once a second sync confirms it is gone.
- The words of every notification, composed here for both apps: an amount, a direction and whether the chain has the transaction yet. While amounts are hidden there is no amount, and when the app asks for no details there is neither wallet nor amount. Three transactions per wallet and sync are said one by one and the rest counted in one line, and a payment no longer coming always gets a notification of its own. The process holds a budget of 20 notifications a minute, and 20 more for the payments no longer coming. A wallet name longer than a title allows is cut at 63 characters followed by "…", and a control character in it becomes a space.
- Encrypted storage. The vault is sealed with XChaCha20-Poly1305 under a key the platform keeps, and one process at a time opens it (`VaultError::AlreadyOpen`). The app lock is hashed with Argon2id, and its delay between attempts survives a restart.
- An encrypted backup file, sealed under a password with Argon2id (64 MiB, 3 passes), that carries the wallets from one device to another, and the node settings when asked. A wrong password, a file that is not a backup and a backup from a newer version fail under three different error codes, and a password too short to have sealed any backup counts as a wrong one.
- A wallet of a backup that cannot be watched, for its name or its material, is marked in the preview with the reason (`BackupWalletPreview::refused`). A restore of every wallet leaves it out and names it (`ImportReport::refused`), and one that asks for it by index fails and names it. The preview and the restore follow the same plan, so the preview shows what the restore will do. Restoring the node settings also pins the certificate the backup holds for an Electrum server the vault keeps using, and pins nothing for a host that the backup lists with two different fingerprints. A wallet on the wrong network says which network its keys belong to.
- Every error carries a stable code (`ErrorCode`), and both apps choose their words by that code rather than by the error's text. A sync that failed on a server whose proof did not hold comes as `false_proof`. A wallet that fails in a sync of every wallet, or in a sync started by the live watch, carries the same code (`kind`). Whether a server was down, and goes behind the others, is decided by the kind of its failure, never by its words.
- One typed record in the vault for the preferences both apps share: the unit, hidden amounts, the fiat value with its currency and its source, the alerts and the warning before an explorer opens, each with its default. The currency wins: picking one the source does not quote moves the source to one that does. None of it goes into a backup.
- Fiat price from the wallet manager, in the currency and from the source of the shared preferences, with the table of currencies each source quotes and a refresh every 60 seconds. The sources are mempool.space, the default for the seven currencies it quotes, and CoinGecko, whose prices come with the credit its terms ask for (`Credit`). A stored `kraken` preference reads as `mempool_space`, and mempool.space's price history is asked for in one currency only. The request takes the route the syncs take: through Tor when a backend is an onion address, and not sent at all when Tor cannot be reached.
- An update check decided here for both apps, with its record kept in the vault. It goes out at most once a day, the first time a day after the first session, never announces a pre-release, names the GitHub API version it expects, and compares versions by SemVer, so a `0.2.0` is announced to someone running `0.2.0-rc.1`. A release the user closed stays closed. It takes the same route as the price, but the check a session makes never starts Tor for itself: on a day it needs Tor and none is running, it sends nothing, the day does not count, and the next session asks again.
- CSV export of a wallet's transactions, filtered by date and direction.

### Security

- A private key is refused wherever it comes from: the parser, a backup file, an export that hides it behind JSON escapes, and a last check as each wallet is created. An error never quotes it.
- What a server sends is bounded. Every Esplora answer is capped once decompressed, a sync keeps at most 256 MiB of the transactions it reads, and no HTTP client follows a redirect to another host. A server's error or refusal reaches the app as one short line, without control characters or bidirectional marks.
- A server cannot make up a confirmation. Each one is proven in its block, over Electrum as over Esplora: the merkle branch must lead to the header's root, read the way Electrum reads it against CVE-2012-2459 and CVE-2017-12842. On mainnet, the header must carry the target of its retarget period, from a table drawn from Electrum's checkpoints, and past the table no easier than consensus allows. Over Electrum, a confirmation in a checkpointed period must also chain to its checkpoint. Over Esplora too, a confirmation from before March 2014, a period where forging a header costs a few dollars, must chain to its checkpoint; if the server stops sending the chain halfway, the confirmation stays unconfirmed. Every tip a server gives must carry the work of its height, including the tip a sent transaction or a watched address counts its confirmations from. When the wallet holds the transaction that paid a coin, the server's description of that coin must match it. A false proof refuses the server.
- A server of another network is refused by its genesis block. Block headers are taken only as a linked chain, under a tip height the chain can have reached. A transaction worth more than 21 million bitcoin, one that spends the same coin twice, and amounts that overflow are refused like a failed server.
- A `.onion` name never reaches the system resolver: server addresses go through the URL parser of the HTTP client, and an Electrum host that hides a port is refused.
- The built-in Tor client is arti 2.7.0, with its security fixes for clients. A relay can no longer fill memory through half-closed streams, and a directory mirror can no longer do it through the consensus it sends, or stall the client by holding back its answer.
- An animated UR that announces more than 5,000 parts is refused, and so is a QR code nested in another.
- A key derived from a password or a platform key is wiped after use, a failure included, and Argon2 wipes its own working memory.
